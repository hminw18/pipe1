# Pipe1 Web Authentication and Access Control Spec

Login, session, and authorization design for the Pipe1 web app. Platform architecture is in `docs/Web_Architecture.md`; the implemented schema is in `server/` (`src/pipe1_server/models/`, `migrations/`).

Baseline standards: OWASP ASVS 4.0.3 Level 2 (V2 Authentication, V3 Session Management, V4 Access Control, V13 API, V14 Configuration), NIST SP 800-63B for password and authenticator rules, and the OWASP Cheat Sheets for CSRF, session management, and HTTP headers. Accepted deviations are listed in section 13.

## 1. Decisions

| Topic | Decision |
| --- | --- |
| Login ID | Email address |
| Account creation | Admin-issued via email invitation; no self sign-up |
| Organizations | Users belong to one organization; inspectors in the same org can see each other's org-visible projects |
| Project visibility | `private` or `org`, set by owner; no default (the client must choose) |
| Org admin access | Can view and edit private projects in their org; can transfer ownership |
| Org member edit rights | Can edit org-visible projects; delete and visibility change stay with owner and org admin |
| Session | Opaque server-side session; idle timeout 2 hours, absolute 12 hours |
| CSRF | HMAC-signed synchronizer token derived from the session, plus `Origin` check |
| MFA | TOTP, required for `platform_admin`; optional (off by default) for `org_admin` and inspectors |
| Email | Resend |
| Implementation | In-house in FastAPI with vetted libraries: `pwdlib[argon2]`, `pyotp`, `secrets`, `hmac` |

## 2. Roles and Permissions

| Role | Who | Capabilities |
| --- | --- | --- |
| `platform_admin` | Pipe1 operator staff | Create organizations and their first org admin; deactivate organizations. Separate admin area behind IAP. MFA required. No access to customer project data. |
| `org_admin` | Customer manager | Invite/deactivate users in own org, change roles, reset a user's MFA, transfer project ownership, view org audit log. MFA optional. |
| `inspector` | Field user | Create projects, set visibility, work on accessible projects. |

Project permission matrix (all access is confined to the user's own organization):

| Action | Owner | Org member, `org` project | Org member, `private` project | Org admin |
| --- | --- | --- | --- | --- |
| View | yes | yes | no | yes |
| Edit businesses/reports/videos/defects, export | yes | yes | no | yes |
| Rename project, change visibility | yes | no | no | yes |
| Delete project | yes | no | no | yes |
| Transfer ownership | no | no | no | yes (to a member of the same org) |

Rules:

- Businesses, reports, videos, defects, captures, and exports inherit access from their project.
- Any resource the user cannot view returns `404`, never `403`, whether it belongs to another organization or is a private project in the same organization, so existence is not revealed.
- Every org-admin read or write on a project they do not own is recorded in the audit log.
- Platform admins have no organization and therefore no access to project data; row-level security enforces this. Support access to customer data, if ever needed, requires a separate, time-limited, customer-approved and audited mechanism designed at that time.
- UI copy for private: `비공개 (본인 및 관리자만)`.

## 3. Data Model

Implemented in `server/src/pipe1_server/models/auth.py` and `migrations/versions/0001_initial_schema.py`.

```text
organizations(id, name, status[active|disabled], created_at)
users(id, organization_id NULL for platform_admin, email unique lowercase, role,
      status[invited|active|disabled], mfa_required, created_at, last_login_at)
      unique(id, organization_id)  -- lets other tables require "a user of this org"
password_credentials(user_id pk, hash, updated_at)
mfa_totp(user_id pk, secret_ciphertext, confirmed_at, last_used_step)
recovery_codes(id, user_id, code_hash, used_at)
sessions(id, user_id, token_hash unique, authenticated_at, last_seen_at,
         idle_expires_at, absolute_expires_at, ip, user_agent, revoked_at, created_at)
login_challenges(id, user_id, token_hash unique, expires_at, attempt_count, used_at, created_at)
invitations(id, organization_id, email, role, token_hash unique, invited_by,
            expires_at, used_at, revoked_at, created_at)   -- one open invitation per email
password_resets(id, user_id, token_hash unique, expires_at, used_at, created_at)
email_changes(id, user_id, new_email, token_hash unique, expires_at, used_at, created_at)
login_throttle(key pk, failure_count, window_started_at, locked_until)
audit_events(id, organization_id, actor_user_id, action, target_type, target_id,
             ip, user_agent, metadata jsonb, created_at)

inspection_projects(id, organization_id, owner_user_id, visibility[private|org], project_name, ...)
  (owner_user_id, organization_id) → users(id, organization_id)
```

Rules:

- IDs are UUIDv7, generated by the application (`pipe1_server.ids.uuid7`).
- Emails are trimmed, NFKC-normalized, and lowercased before storage and lookup; a check constraint rejects non-lowercase values and a unique constraint enforces one account per email.
- Session, invitation, reset, email-change, and login-challenge tokens are 256-bit values from `secrets.token_urlsafe(32)`. Recovery codes carry at least 80 bits of entropy. All are stored only as SHA-256 digests (a 32-byte check constraint enforces this); the raw value exists only in the response or email that delivers it.
- TOTP secrets are 160-bit and encrypted with a Cloud KMS key before storage.
- Credentials live in their own table so OIDC/SAML SSO can be added later without changing `users`.
- Users are deactivated, never hard-deleted, to keep audit history intact.

## 4. Passwords

- Length: minimum 12 characters, maximum 128. Spaces and all Unicode allowed; NFKC-normalized before hashing.
- No composition rules and no periodic forced rotation.
- Rejected: passwords in a breached-password corpus, and passwords containing the user's email local part or `pipe1`. Corpus source is an open decision: HIBP k-anonymity range API (only a 5-character SHA-1 prefix leaves the server) or a bundled offline list.
- Hashing: Argon2id via `pwdlib`, parameters at or above OWASP minimums (m=19 MiB, t=2, p=1). Rehash on successful login when parameters change.
- Password change requires the current password, revokes all other sessions, outstanding password-reset tokens and login challenges, and sends a notification email.
- Passwords are never logged, emailed, or visible to admins.

## 5. Login

Endpoint: `POST /api/auth/login` with `{email, password}`.

1. Normalize the email, then apply throttling (section 8) keyed by the normalized email and the client IP, before any credential work. Throttling applies identically to emails that have no account, so lockout behavior does not reveal account existence.
2. Look up the user. If not found, still verify against a fixed dummy Argon2id hash so response time does not reveal account existence.
3. On any failure (unknown email, wrong password, invited, disabled, disabled org) return the same `401` and message: `이메일 또는 비밀번호가 올바르지 않습니다.`
4. If the user has MFA enrolled or required, create a `login_challenges` row (expires in 5 minutes) and return `{mfa_required: true}` with the challenge token in a `__Host-pipe1_mfa` cookie (`HttpOnly; Secure; SameSite=Strict; Path=/`; the `__Host-` prefix requires `Path=/`). No session exists yet. The account failure counter is not cleared by a correct password here; it is cleared only when the full login (including MFA) succeeds, so a password holder cannot reset the MFA guessing limit by logging in again.
5. `POST /api/auth/mfa` accepts a TOTP code or a recovery code:
   - At most 5 attempts per challenge; each failure increments `attempt_count` and also counts toward the account throttle. The 5th failure invalidates the challenge.
   - TOTP accepts the current step ±1 and rejects any step at or before `last_used_step` (no replay).
   - Recovery codes are single use.
   - Success marks the challenge used.
6. On success: create a new session (never reuse a pre-login identifier), set the session cookie, set `authenticated_at`, update `last_login_at`, write an audit event, and rehash the password if needed.

## 6. Sessions

- Opaque random token in cookie `__Host-pipe1_session` with `HttpOnly; Secure; SameSite=Lax; Path=/`. No tokens in localStorage, sessionStorage, or URLs.
- Stored server-side in `sessions` (Cloud SQL), looked up by SHA-256 of the cookie value. Cloud Run instances hold no session state.
- Idle timeout: 2 hours since the last authenticated request or heartbeat.
- Absolute timeout: 12 hours since login, regardless of activity.
- Heartbeat: the frontend calls `POST /api/auth/heartbeat` every 5 minutes while the tab is in active use or a video is playing, so long video reviews are not counted as idle.
- Warning: the frontend shows a dialog 2 minutes before either timeout. `계속 작업` resets only the idle timer, never the absolute timer.
- Expiry: the frontend shows an in-place re-login dialog without a page reload. Report autosave ensures no work is lost.
- Revocation: logout deletes the session server-side. Password change/reset, deactivation, role change, MFA reset, and org deactivation revoke all of the user's sessions immediately.
- Users can list their active sessions and revoke any or all (`로그아웃 (모든 기기)`).
- Re-authentication: email change, MFA disable, project delete, ownership transfer, and role change require `authenticated_at` within the last 10 minutes; otherwise the client must re-enter the password (plus MFA if enrolled), which updates `authenticated_at` on the existing session.
- Timeouts are configurable per deployment: `PIPE1_SESSION_IDLE_TIMEOUT_SECONDS=7200`, `PIPE1_SESSION_ABSOLUTE_TIMEOUT_SECONDS=43200`.
- No cap on concurrent sessions per user.

## 7. CSRF and Browser Security

- Frontend and API are served from the same origin (`/` and `/api`); CORS is not enabled on the API.
- CSRF token: `HMAC-SHA256(csrf_key, session_id)`, base64url-encoded. `csrf_key` lives in Secret Manager. The token is returned by `GET /api/auth/me`, so it survives page reloads, and changes whenever the session changes. Nothing is stored.
- Every state-changing request (`POST`, `PUT`, `PATCH`, `DELETE`) must:
  - carry an `Origin` header equal to the app origin (requests without `Origin` are rejected),
  - carry `X-CSRF-Token`, compared with `hmac.compare_digest` against the expected token, and
  - send any body as `Content-Type: application/json` (requests without a body, such as `DELETE`, need no content type), so plain HTML forms, which always send a form content type, cannot reach the API.
- Response headers on every response:
  - `Strict-Transport-Security: max-age=63072000; includeSubDomains`
  - `Content-Security-Policy: default-src 'self'; img-src 'self' https://storage.googleapis.com; media-src 'self' blob: https://storage.googleapis.com; connect-src 'self' https://storage.googleapis.com; style-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'`. No `'unsafe-inline'` or `'unsafe-eval'`; if a UI library needs inline styles, use nonces.
  - `X-Content-Type-Options: nosniff`
  - `Referrer-Policy: strict-origin-when-cross-origin`
  - `Cross-Origin-Opener-Policy: same-origin`
  - `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()`
  - `Cache-Control: no-store` on all `/api/*` responses
- The media bucket allows CORS only from the app origin (Terraform variable `app_origins`), for direct uploads and video range requests.

## 8. Throttling and Abuse Limits

- Per account key (normalized email, whether or not an account exists): failures 5-10 within 15 minutes add an increasing delay; after 10, the key is locked for 15 minutes. Locks expire automatically; there is no permanent lockout. Password and MFA failures share this counter.
- Per IP: Cloud Armor rate limits on `/api/auth/*`, plus an application-level per-IP counter.
- Password reset and invitation-accept endpoints are rate-limited per email and per IP.
- General API: Cloud Armor per-IP rate limit on `/api/*`.
- Uploads: maximum video size per file and storage quota per organization, enforced when the upload session is created.
- Lockouts and throttle events are audited; spikes trigger a Cloud Monitoring alert.

## 9. Account Lifecycle

### 9.1 Organization onboarding

1. `platform_admin` creates the organization and invites its first `org_admin`.
2. The org admin accepts the invitation and sets a password. TOTP is optional and can be enabled later in settings.

### 9.2 Invitation

1. Org admin submits email and role.
2. Server creates an invitation token (single use, expires in 72 hours) and queues the invite email.
3. The invitee opens the link and sets a password (section 4). Only platform admins must also enroll TOTP; everyone else may enable it in settings.
4. The user becomes `active`; the invitation is marked used.
5. Re-sending an invitation revokes the previous token (the database allows one open invitation per email).
6. Inviting an email that already has an account is rejected with `초대할 수 없는 이메일입니다.` This reveals to the org admin that the address is registered somewhere; it is accepted because only authenticated admins can ask, invite creation is rate-limited per admin, and every attempt is audited.

### 9.3 Password reset

1. `POST /api/auth/password-reset` always returns the same response: `계정이 존재하면 재설정 메일이 발송됩니다.` Email is sent asynchronously, so timing is identical either way.
2. Token is single use and expires in 30 minutes; requesting a new one invalidates older ones.
3. Completing the reset sets the new password, revokes all sessions, outstanding reset tokens, and login challenges, and sends a confirmation email. The user is never logged in automatically; they sign in with the new password (and MFA).
4. Deactivated and invited-but-not-accepted users cannot reset passwords.

### 9.4 Email change

Requires re-authentication, a confirmation link sent to the new address (single use, 30 minutes), and a notification to the old address. Completing it revokes outstanding password-reset tokens.

### 9.5 MFA

- Enrollment: show QR code and secret, require one valid code to confirm, then issue 10 recovery codes (shown once, stored hashed).
- Lost device: org admin resets the user's MFA (audited, sessions revoked, user notified by email); the user re-enrolls at next login. Platform admins reset org admins.
- Passkeys (WebAuthn) may be added later as an additional factor.

### 9.6 Deactivation

- Takes effect immediately and revokes all sessions and login challenges.
- The user's projects remain; org admin can transfer ownership.
- Deactivated users cannot log in, reset passwords, or accept invitations.

## 10. Authorization Layer

1. A single FastAPI dependency (`current_user`) resolves the session cookie, enforces timeouts, verifies `Origin`, CSRF token, and content type on state-changing methods, and loads the user and organization. Routes never read the session themselves.
2. A single policy module implements the matrix in section 2: `authorize(user, project, action)`.
3. Every route resolves its target up to the owning project (defect → report → report group → business → project) and calls `authorize` before any read or write. No route fetches a row by bare ID without this.
4. List endpoints use one scoped query helper that always applies:
   `organization_id = :org_id AND (visibility = 'org' OR owner_user_id = :user_id OR :is_org_admin)`.
5. PostgreSQL row-level security is the backstop (implemented in migration `0001`):
   - The app connects as `pipe1_app`, which does not own the tables; `pipe1_migrator` owns them and is used only by Alembic.
   - Each request transaction starts with `pipe1_server.db.set_access_context()`, which sets `app.org_id`, `app.user_id`, `app.role` transaction-locally. Without a context, no project data is visible.
   - `inspection_projects` has separate SELECT/INSERT/UPDATE/DELETE policies matching the matrix; every table below it carries `project_id` (kept consistent by composite foreign keys) and a policy that calls `app_can_access_project(project_id)`.
   - `pipe1_app` may only `SELECT` and `INSERT` on `audit_events`.
6. Files: private bucket; object keys under `org/{org_id}/project/{project_id}/...`, chosen by the server. Clients never supply storage paths. Signed URLs are issued only after `authorize`:
   - Images and exports: V4 signed GET, valid 5 minutes; exports use `Content-Disposition: attachment`.
   - Video playback: V4 signed GET, valid 60 minutes; the player requests a fresh URL when one expires and resumes at the same position.
   - Uploads: signed resumable session bound to the server-chosen key and a maximum size.
7. Internal endpoints (Cloud Tasks → worker) are not reachable from the internet (Cloud Run ingress `internal`) and verify the Google-signed OIDC token of the Cloud Tasks service account. Each task carries the requesting user and organization; the worker sets the same access context and re-checks authorization.
8. The API's Cloud Run service uses ingress `internal-and-cloud-load-balancing`, so Cloud Armor cannot be bypassed through the `run.app` URL.

## 11. Email (Resend)

- Sending domain verified in Resend (DKIM, plus SPF and MX on the `send` return-path subdomain); DMARC record published, starting at `p=quarantine`.
- API key with "Sending access" only, restricted to the sending domain, stored in Secret Manager, readable only by the mailer service account.
- Click tracking and open tracking disabled on the sending domain (Resend's default) so token links are not rewritten through a third-party domain.
- Templates (Korean) live in the repository (`server/src/pipe1_server/email/templates.py`), are HTML-escaped, and are rendered by the worker, so wording is reviewed and versioned with the code and needs no manual setup in Resend: invitation, password reset, password changed, email-change confirmation, email-changed notice to old address (new address masked), MFA reset notice. A new-device login notice is optional and not yet implemented.
- Token links put the token in the URL fragment (`/invite#token=...`), which browsers never send to servers, so tokens stay out of access logs and `Referer` headers.
- Emails are sent from a Cloud Tasks job, not inside the HTTP request, so provider latency or outages do not affect login responses or reveal account existence.
- If Resend webhooks are used, their signature is verified; bounced invitations are shown to the org admin.
- Development and CI use the console sender or a fake mail backend (Resend's `delivered@resend.dev` test address for live checks).
- Resend processes recipient email addresses outside Korea; this must be disclosed in the Privacy Policy (see `docs/Web_Architecture.md` §8).

## 12. Audit and Monitoring

Audited actions: login success/failure, logout, lockout, MFA challenge failure, MFA enroll/reset/disable, password change/reset, email change, invitation create/resend/accept/revoke, role change, deactivation, session revoke, project visibility change, project delete, ownership transfer, org-admin access to non-owned projects, exports.

- Logs never contain passwords, tokens, session IDs, CSRF tokens, TOTP secrets, or recovery codes.
- Audit events contain personal data (IP address, user agent). Retain them for at least 1 year to meet the access-record requirement for personal-information processing systems under Korean law (confirm the exact period with counsel), then delete.
- Org admins can view their organization's audit log; platform admins can view all.
- Alerts: failed-login spikes per IP or account, any `platform_admin` action, elevated `401/403/404` rates on resource endpoints.

## 13. Accepted Deviations

| Requirement | Standard | Pipe1 | Reason |
| --- | --- | --- | --- |
| Idle session timeout | ASVS 4.0.3 V3.3.2 (L2): 30 minutes | 2 hours | Long video review sessions. Compensated by 12-hour absolute timeout, heartbeat-based activity, MFA for platform admins (optional for org users), session list with global logout, Cloud Armor rate limiting, and audit logging. |

### Authorization matrix test suite

For every API endpoint, run as: owner; same-org member on an `org` project; same-org member on a `private` project; org admin; user from another org; platform admin; deactivated user; no session. Assert the expected status for each. This suite runs in CI and blocks merges on failure. The database-level equivalent already exists in `server/tests/test_row_level_security.py`.
