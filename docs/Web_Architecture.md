# Pipe1 Web Architecture

Target architecture and migration plan for moving Pipe1 from the PySide6 desktop app to a multi-user web app on Google Cloud. Product behavior is defined in `docs/Product_Requirements.md`; login and access control in `docs/Web_Auth_Spec.md`.

Status: built, not yet deployed. `core/` (shared Qt-free code), `server/` (API, worker), `web/` (frontend), `infra/terraform/` and `.github/workflows/` implement this document and `docs/Web_Auth_Spec.md`; nothing is deployed until a domain, Resend account and `terraform apply` are in place. No real users or license holders exist, so no customer data or license migration is required.

## 1. Decisions

| Topic | Decision |
| --- | --- |
| Backend | Python + FastAPI, reusing the Qt-free core: `db.py` logic, `services/`, `stop_detection/`, `defect_taxonomy.py`, `state_grading.py` |
| Frontend | React + TypeScript; API types generated from FastAPI's OpenAPI schema |
| Cloud | Google Cloud, region `asia-northeast3` (Seoul) |
| Database | Cloud SQL for PostgreSQL 17, SQLAlchemy + Alembic, row-level security as the access-control backstop |
| Files | Cloud Storage (private bucket) |
| Login | Email + password, admin-issued accounts (see `docs/Web_Auth_Spec.md`) |
| Email | Resend |
| Not ported | `licensing/`, `updates/`, DPAPI, device identity, PyInstaller/WiX packaging |

Why Python stays: the heavy work runs in native code (OpenCV/numpy, ffmpeg, PostgreSQL), the PDF layout and detectors are already tuned, and future AI detection will be Python. CPU-heavy jobs run in separate worker processes, not in the API process.

## 2. Target Architecture

```text
Browser (React + TS)
   │  same origin: https://app.<domain>/      → static frontend
   │                https://app.<domain>/api  → API
   ▼
External HTTPS Load Balancer + Cloud Armor (WAF, per-IP rate limits)
   ├── Backend bucket + Cloud CDN  → React build
   └── Serverless NEG → Cloud Run "api" (FastAPI)
                          ├── Cloud SQL PostgreSQL (private IP)
                          ├── Cloud Storage (videos, captures, reports)
                          ├── Secret Manager / Cloud KMS
                          └── Cloud Tasks ──► Cloud Run Jobs / "worker" service
                                               ├── video remux/transcode (ffmpeg)
                                               ├── stop detection (OpenCV)
                                               ├── Excel/PDF generation
                                               └── email sending (Resend)
```

## 3. GCP Components

| Need | Service | Notes |
| --- | --- | --- |
| API | Cloud Run | Stateless; sessions live in PostgreSQL. Ingress `internal-and-cloud-load-balancing`, so traffic cannot bypass the load balancer and Cloud Armor through the `run.app` URL. All egress goes through its own subnet with Cloud NAT (for the breached-password API), so calls to the internal-only worker stay inside the VPC. The API image has no ffmpeg. Request bodies are limited (32 MB on HTTP/1), so videos never pass through the API. |
| Background work | Cloud Run `worker` service, triggered by Cloud Tasks; Cloud Run `mailer` service for email | Same image. The worker processes media and runs jobs: larger CPU/memory, one request per instance, ingress `internal`, all egress through a subnet without NAT, so it reaches only Google APIs (Private Google Access) and the database. The mailer only sends email (it needs the internet for Resend) and has no database or media access. Every task carries a Google-signed OIDC token that the service verifies; synchronous capture calls from the API carry the API service account's token. Compute Engine only if GPUs are needed later. |
| Database | Cloud SQL for PostgreSQL 17 | Private IP only, TLS required, automated backups, point-in-time recovery. Roles: `pipe1_migrator` owns the schema (Alembic only); `pipe1_app` is the runtime role, subject to row-level security. Role passwords are generated by Terraform and stored in Secret Manager; moving to IAM database authentication is a follow-up. |
| Object storage | Cloud Storage | Uniform bucket-level access, public access prevention, CORS limited to the app origin. Signed URLs and resumable uploads as in `docs/Web_Auth_Spec.md` §10. |
| Edge | External HTTPS Load Balancer, Cloud CDN, Cloud Armor | One origin for frontend and API so cookies need no CORS. OWASP CRS rules; rate limits on `/api/auth/*` and `/api/*`. |
| Secrets | Secret Manager, Cloud KMS | DB role passwords, CSRF signing key, Resend API key (added by hand so it never enters Terraform state); KMS key encrypts stored TOTP secrets. Terraform state holds generated passwords, so the state bucket is restricted to project administrators. |
| Platform admin area | Identity-Aware Proxy | Extra Google-identity gate in front of the platform-admin UI. |
| Observability | Cloud Logging, Error Reporting, Cloud Monitoring | Structured JSON logs; alerts on failed-login spikes, job failures, 5xx rate. |
| CI/CD | Cloud Build or GitHub Actions, Artifact Registry | Workload Identity Federation (no service-account JSON keys); one least-privilege service account per Cloud Run service. |
| Infrastructure | Terraform | All of the above declared as code. |

Check before committing to GCP for public-sector customers: whether they require a CSAP-certified cloud and whether the chosen GCP region qualifies.

## 4. Video Pipeline

1. **Upload**: the browser requests an upload session from the API (after access check, size limit, and organization quota check), then uploads the video directly to Cloud Storage with a signed resumable upload bound to a server-chosen key. Multi-GB files and flaky connections are expected. The report's video row is created when the upload starts (status `uploading`). Meanwhile the browser plays the chosen file from the user's disk (`blob:` URL), so review and capture start immediately instead of after upload and processing.
2. **Validate**: uploaded files are untrusted input to complex parsers (ffmpeg, OpenCV). The worker first runs `ffprobe` with a timeout and accepts only expected containers and codecs (`.avi`, `.mkv`, `.mov`, `.mp4`; video streams only). Rejected files are deleted and the video marked `failed`.
3. **Playback copy**: sources that are already 8-bit 4:2:0 H.264 (most CCTV recorders) are only repackaged into an MP4 with the index first (`-c copy +faststart`, about a minute for a 2 GB file); anything else is transcoded to H.264 with a keyframe every 2 s. The timeline thumbnail strip is built from keyframes only, falling back to a full decode when keyframes are too sparse. The original is kept. Media processing runs only in the worker: a separate service account limited to the media bucket and its own secrets, CPU/memory/time limits per job, no inbound internet traffic, and outbound traffic only to Google APIs. A crafted file can therefore damage at most one job, not the API or the database credentials of other services.
4. **Playback**: HTML5 `<video>` with a signed URL valid 60 minutes; the player fetches a fresh URL when one expires, keeping the current position. Frame stepping uses `requestVideoFrameCallback` where available.
5. **Capture**: while the user plays their local file, the browser grabs the shown frame at full resolution as PNG and sends it with `timestamp_ms`; the worker accepts only a PNG of bounded size (checked in the header before decoding), re-encodes it, and reads the depth counter from it. Otherwise (the processed copy is playing) the browser sends only `timestamp_ms` and the worker extracts the frame from the original with ffmpeg. Either way the image is stored under a new key unique to the defect. Browser frames are lossless and show exactly what the user saw; colour conversion may differ slightly from ffmpeg's.
6. **Stop detection**: runs as a background job in the worker once processing is done; the UI shows progress by polling.
7. **Jobs on a single host** (dev VM): jobs run on worker threads in the API process (`PIPE1_JOB_QUEUE=background`); jobs left queued or running by a restart are resumed at startup. Production relies on Cloud Tasks retries.

Video timestamps must be derived consistently between playback, capture, and analysis (same decoder backend, time-based rather than frame-index-based seeking) so defect markers and stop segments line up.

## 5. Data Layer

Implemented in `server/` (models in `src/pipe1_server/models/`, migration `migrations/versions/0001_initial_schema.py`).

- PostgreSQL schema ported from `db.py`, managed with Alembic migrations (versioned, run once per deploy as `pipe1_migrator`, never on every request or startup).
- Hierarchy: `inspection_projects` → `businesses` → `report_groups` → `reports` → `manholes`, `pipe_information`, `actual_survey_information`, `report_videos`, `report_defects`.
- Report versions: `report_groups` holds the identity shared by all versions (`report_number`, `pipe_number`, unique per business); `reports` holds one row per version (`version_number`, `version_name`, and the survey/location fields). This replaces the desktop's self-referencing `version_group_id`.
- Every project carries `organization_id`, `owner_user_id`, `visibility`. Every table below it carries `project_id`, tied to its parent by a composite foreign key such as `(business_id, project_id) → businesses(id, project_id)`, so it cannot disagree with the real parent. Row-level security uses it to decide access with one project lookup.
- Desktop rules enforced as constraints: one video per report; a defect's video belongs to the same report; a defect records either a defect item or a condition item, and only defects carry a grade; `distance_m` is required; each defect image has a unique object key.
- Manhole fields stay text, including numeric-looking ones (elevation, depth, coordinates), because the desktop accepts free text there.
- All timestamps stored as UTC `timestamptz`; convert to KST only for display. (The desktop DB mixes KST `updated_at` with UTC `created_at`.)
- Files are referenced by storage object keys, never absolute paths. Object keys: `org/{org_id}/project/{project_id}/report/{report_id}/...`.
- Update endpoints apply partial updates (PATCH semantics); fields not sent are left unchanged.
- IDs are UUIDv7, generated by the application.

## 6. Fixes to Carry Into the Port

Issues found in the desktop code that must not be reproduced in the web backend:

| Issue | Desktop location | Web requirement |
| --- | --- | --- |
| Two defects captured at the same timestamp share one image file; deleting one deletes the other's image | `services/storage_service.py` `capture_path` | Unique object key per defect |
| Capture image written before distance validation, leaving orphans on failure | `services/inspection_service.py` `capture_and_save_defect` | Validate first, then write |
| Detectors decode every frame while sampling at 1-5 fps | `stop_detection/depth_ocr_detector.py`, `frame_candidate_detector.py` | `grab()` alone still decodes every frame. The distance reader now decodes keyframes only (ffmpeg `-skip_frame nokey`) and decodes frame by frame only around stops, unreadable keyframes and long keyframe gaps; without the ffmpeg command (desktop) it falls back to every frame. The candidate stage still decodes each stop in full. |
| Depth counter read by matching digit templates cut from one recorder's `ddd.d` counter; other recorders' counters (e.g. `013.50m`) read as nothing, so stop analysis finds no stops and captures get no distance | `stop_detection/depth_ocr_detector.py` `CommonDepthDigitMatcher` | Pretrained text recognizer (PP-OCRv4 on ONNX Runtime, `models/ocr/`, `stop_detection/text_reader.py`), limited to the counter's characters, so any font and format reads. The desktop keeps the templates until onnxruntime is bundled. |
| Player and analysis use different OpenCV backends / frame-index seeking | `ui/main_window.py`, `stop_detection/video_capture.py` | One shared time-based decode path |
| User text starting with `=` becomes an Excel formula | `services/report_service.py` | Write user text as literal strings |
| Full-resolution PNGs embedded in Excel/PDF | `services/report_service.py`, `pdf_report_service.py` | Embed downscaled JPEG thumbnails |
| Partial update payload sets missing fields to NULL | `db.py` `update_report`, `update_defect` | PATCH semantics |
| File deletes trust paths stored in the DB | `services/inspection_service.py` | Only delete keys under the resource's own prefix |
| Migrations run on every startup | `db.py` `_run_migrations` | Alembic, versioned |
| Stop analysis logic lives in the UI module | `ui/main_window.py` `StopAnalysisWorker` | Move into `stop_detection` / a service before porting |

## 7. Migration Phases

1. **Extract the core (desktop stays shippable)**: done. Qt-free modules live in `core/` (`pipe1_core`), used by both apps; stop analysis moved out of the UI; section 6 fixes applied in shared and desktop code.
2. **Infrastructure and auth**: done in code. Migrations `0001`-`0002` with row-level security; auth phases 1-5; Terraform for every component in section 3 (planned, not applied).
3. **API**: done. Project/Business/Report CRUD and duplication, versions, video upload/transcode, capture, defects, stop detection and export jobs; every route behind the authorization layer.
4. **Frontend**: built (`web/`): navigation, report forms, video player and capture, defect list, export, settings, admin screens. Browser QA against a deployed environment still to do.
5. **Hardening and launch**: CI with tests, audits and secret scanning is in place. Open: deploy, browser QA, ASVS review sign-off, ZAP scan, external penetration test, legal documents (section 8).

The desktop app remains available until the web app reaches feature parity.

## 8. Legal and Compliance Checklist

Required before the first real customer:

- Terms of Service
- Privacy Policy (개인정보 처리방침) under the Korean Personal Information Protection Act
- Training-data consent text (if training upload is enabled; see section 9)
- Third-party open-source notices
- Font license notice (Pretendard)

In-app surfaces:

- Links to Terms and Privacy Policy on the login page and in settings
- Training-data opt-in/out control for org admins
- Current legal document versions visible in settings

The Privacy Policy must explain what data is stored, where (GCP Seoul), how long it is retained, how deletion requests are handled, and that customers are responsible for the content of inspection videos they upload. It must also cover, under the Personal Information Protection Act:

- The designated privacy officer (개인정보 보호책임자) and contact details.
- Processing outsourcing (처리위탁): Google Cloud (hosting, storage, logs) and Resend (email delivery).
- Overseas transfer (국외 이전): Resend processes recipient email addresses in the United States; disclose the recipient, country, items, purpose, and retention, and obtain consent or rely on another lawful basis as counsel advises. If the HIBP password check is adopted, document it as well.
- Retention of access/audit records (see `docs/Web_Auth_Spec.md` §12).

Have counsel review the final text.

## 9. Training Data Policy (Summary)

Kept from the desktop training-upload requirements; the implementation will be server-side because data already lives on the server.

- Training use requires explicit consent, separate from account creation and the Terms of Service. Consent is recorded per organization with type, version, accepted/revoked timestamps, and the user who changed it.
- Consent levels: `none`; `capture_images_and_labels` (default when enabled); `extended_report_context` (requires separate consent text).
- Default training payload: capture image, defect/condition labels, item category, pipe type, category, specification, drive direction, distance, timestamp, grade, quadrant.
- Never included by default: source videos, generated Excel/PDF files, project/business/client names, road address, lot number, manhole coordinates, inspector/contractor names, freeform memo.
- Revocation stops future use; deletion of already-copied data follows the Privacy Policy.
- Training copies live in a separate bucket/dataset with its own access controls and no customer-identifying fields.
